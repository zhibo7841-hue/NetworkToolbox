## Privacy / Security

- The checked manifest requests `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`, and `CHANGE_WIFI_MULTICAST_STATE`. These correspond to user-initiated Ping/DNS/TCP/Traceroute/LAN/WoL and Wi-Fi/mDNS discovery. No location, nearby-device, account, ads, or analytics permission was found in the checked manifests.
- History and Saved Device Profiles (including custom names and WoL config) use local Room. `allowBackup=false`. No analytics/cloud-upload SDK or automatic report upload was identified in the Gradle/source review. Explicit user-initiated PDF save/share is a separate export action; sharing can send the user's chosen report to another app.
- Network probes necessarily contact chosen targets; mDNS/SSDP/UPnP and WoL send LAN traffic. `usesCleartextTraffic=true` exists for the local UPnP HTTP description path; its broad app-level scope is worth a later policy review, but is not by itself evidence of uploading inventory. The UPnP fetch path validates advertised locations and disables redirects.
- `git ls-files` found no tracked `local.properties`, `key.properties`, `*.jks`, `*.keystore`, or private-key file. A targeted tracked-file pattern scan found no known API-key/token/private-key signature. Local `key.properties` and keystore are ignored. Pattern scans are not a complete secrets audit; do not print or commit signing values.
- No confirmed secret/privacy release blocker was found. No runtime data-exfiltration test was conducted.

- Current Gradle and Debug APK metadata: package `com.networktoolbox`, `versionName=0.4.0`, `versionCode=4`, `minSdk=31` (Android 12), `targetSdk=36` (Android 16), `compileSdk=36`. A v0.5 release needs a deliberate monotonic code/name bump; **this audit did not change them**.
- Local release-signing DSL exists and reads ignored `key.properties`. This workstation has all four required nonempty keys and the referenced keystore path exists; secret values were not printed. This establishes *configuration presence*, not successful current-source signing or identity continuity. Verify the produced signed APK and signing certificate against the published release lineage in RC preparation.
- A Debug APK exists. The pre-existing `app/build/outputs/apk/release/app-release.apk` is dated 2026-09-07 and is **stale**, not a v0.5 artifact. No Release build was run in this audit because it would invoke the local signing secret and the task asks only to audit configuration. Do not upload the stale APK.
- `zipalign -c -P 16 4` passes for the current Debug APK. Both packaged native libraries (`libnetworktoolbox_traceroute.so`, `libandroidx.graphics.path.so`) have 0x4000 ELF LOAD alignment for arm64-v8a, armeabi-v7a, x86, and x86_64. Recheck the actual signed RC APK; a Debug check is not a final Release-artifact check.
- GitHub Release should use a signed APK for direct installation. An AAB may be considered only for a separately approved store channel; no channel change is authorized here.
- Public [GitHub Releases](https://github.com/zhibo7841-hue/NetworkToolbox/releases) currently lists `v0.4.0` as Latest. Local tags stop at `v0.4.0`. No v0.5 tag or GitHub Release is created by this audit.

## Known Issues

No presently reproducible app crash was established from this audit. The following require explicit disposition, not silent promotion to feature blockers:

1. Sony/Android 16 final regression is not performed on the final signed v0.5 RC APK; previous device reports cover individual increments, not one immutable candidate.
2. Intermittent/concurrency test history has no reproducible current failing case in this checkout; the up-to-date Gradle test gate cannot close that risk.
3. Lint has 33 warnings (0 errors); two `InlinedApi` warnings reference `NsdManager.FAILURE_BAD_PARAMETERS` in mDNS. Source uses this as an inlined error code, but Android 12–16 compatibility should be confirmed in RC rather than assuming all warnings are meaningless.
4. The UPnP HTTP fetcher still sends `User-Agent: NetworkToolbox/0.2.0`, a stale presentation token. Do not treat it as an application version or as proof of a network fault; consider it low-priority polish.
5. VAIO wake compatibility/settings are unresolved per maintainer, while one main machine has successfully woken. WoL does not guarantee wake for every device.
