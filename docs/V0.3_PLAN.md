# NetworkToolbox v0.3.0 Plan

> Status: Ready for Release
>
> Version: v0.3.0

## Release Goal

NetworkToolbox v0.3.0 will add two evidence-based capabilities:

- **LAN Device Identification Phase 1:** enrich already discovered LAN devices
  with locally observed, source-labelled identification information where it is
  available.
- **Traceroute Phase 1:** provide a reliable, cancellable path-checking tool
  with understandable results and cautious troubleshooting context.

The release continues the local-first model: no account, no cloud device
identification API, no upload of LAN results, and no user device profiling.

## Scope

### LAN Device Identification Phase 1

**Status: Completed in v0.3.0.**

The existing LAN Scanner v1 discovery pipeline remains the source of online
evidence. Identification is a separate post-discovery enrichment layer:

- **Hostname / Reverse DNS:** attempt reverse DNS and any system-available host
  name for a discovered IPv4 host. If no name is available, retain an unknown
  name rather than guessing.
- **mDNS / Bonjour:** investigate and support locally advertised device names
  and basic service information where Android capability and the local network
  make that reliable.
- **UPnP / SSDP:** investigate and support device-provided Friendly Name,
  Model, Manufacturer, Device Type, and basic service information when openly
  advertised by the device.
- **Source semantics:** each displayed identification result must state its
  actual source, such as Hostname, mDNS, UPnP, Gateway, Local Device, or
  Unknown. A value inferred only from an IP address, open port, or guess is not
  an identification result.

Identification failure, timeout, or missing multicast response does not change
whether a device remains in the discovered-device list. The existing LAN
Scanner discovery Core remains responsible for online evidence.

### Traceroute Phase 1

**Status: Completed in v0.3.0.**

Traceroute is introduced as an independent tool. It will support:

- Domain or IP target input.
- Start and cancellation.
- IPv4, IPv6, and automatic protocol selection.
- Per-hop results with hop number, observed IP when available, latency, and
  timeout/no-response state.
- Basic result interpretation that distinguishes a non-responding intermediate
  hop from a path that can no longer be confirmed.

A non-responding hop is not automatically a broken router or an interrupted
network path. Routers can filter, rate-limit, or decline TTL/ICMP-related
probes while continuing to forward later traffic. User-facing conclusions must
remain evidence-based, for example:

- A destination reached: the path check completed.
- An intermediate hop missing but later hops responding: the path continues;
  the missing hop alone is not a fault finding.
- Repeated non-response from a later stage: the remaining path cannot be
  confirmed; possible causes include routing, upstream, firewall, or target
  policy, without asserting a single cause.

The exact probing mechanism, probe count, Android compatibility constraints,
and timeout policy require a dedicated technical design before implementation.

#### Traceroute Phase 1 UI status

The standalone IPv4 Traceroute Phase 1 UI and presentation layer are now
implemented. The tool has a dedicated entry, target validation, start/stop
interaction, real per-hop progress, three-probe latency presentation, timeout
markers, and conservative explanations for reached, partial, cancelled,
network-changed, and failed results. IPv6, History, PTR, ASN/GeoIP, and
advanced probe configuration remain outside this phase.

## Architecture and Product Boundaries

### LAN Scanner Core is frozen

v0.3.0 identification work must not redesign the validated v0.2.0 discovery
Core or its current safety behavior:

- System reachability and TCP OPEN-only discovery semantics.
- Reachability timeout of 500 ms and TCP timeout of 250 ms.
- Host concurrency of 32 and bounded worker/cancellation behavior.
- Existing fallback-port policy.
- Automatic and custom range validation, RFC1918 restriction, and 254-host
  limit.
- Cellular/VPN restrictions, network-change handling, and one completed-scan
  History record.

The enrichment layer may add source-labelled metadata to discovered devices but
must not remove a device because name or service discovery fails.

### Traceroute remains independent first

Traceroute will not initially rewrite Network Diagnostic. Its data model should
leave room for later diagnostic reuse, but the first implementation priority is
accurate, cancellable standalone behavior on supported Android versions.

### Privacy and permissions

- Reverse DNS, mDNS, and SSDP remain normal local-network probes for the
  current user-selected network; their results remain on device.
- No cloud device identification, online vendor lookup, or uploaded inventory
  is permitted.
- New Android permissions or multicast-related behavior require a dedicated
  technical validation; this plan does not authorize adding permissions.

## Out of Scope

The following are not part of v0.3.0 Phase 1:

- Remote MAC-address collection and OUI vendor databases.
- Cloud identification APIs or device fingerprint databases.
- Active operating-system fingerprinting or deep/broad port scanning.
- Favorite devices and Wake-on-LAN.
- IPv6 LAN address-space enumeration.
- Traceroute maps, GeoIP, ASN data, carrier identification, BGP analysis,
  Looking Glass integration, MTR replacement, or complex path-history
  comparison.
- SSH/Telnet clients, SFTP, automatic repair, and definitive automatic fault
  diagnosis.

## Development Phases

### Task 037 — LAN Device Identification technical baseline

- Audit Android 12–16 constraints, lifecycle requirements, and permission
  boundaries for Reverse DNS, mDNS / Bonjour, and SSDP / UPnP.
- Define enrichment contracts, source semantics, timeout/cancellation policy,
  and local-only privacy constraints.
- Do not change LAN Scanner discovery behavior.

### Task 038 — Reverse DNS / Hostname enrichment

- Implement bounded, cancellable reverse-DNS and system-hostname enrichment for
  already discovered devices.
- Preserve Unknown when no answer is available and record the source of any
  displayed name.

### Task 039 — mDNS / Bonjour enrichment

- Add lifecycle-safe discovery of locally advertised names and basic services
  after an Android technical decision validates the capability.
- Treat the device advertisement as evidence only for the service/name it
  exposes, not as a complete device profile.

### Task 040 — UPnP / SSDP enrichment

- Add bounded parsing of locally advertised SSDP/UPnP metadata after technical
  design approval.
- Display only fields the device openly provides and preserve their source.

### Task 041 — Identification aggregation and UI polish

- Merge source-labelled identification information into LAN Scanner
  presentation without changing the discovery Core, sorting, or online
  semantics.
- Keep unavailable metadata understandable and ensure completed scans/history
  retain their existing safety behavior.

### Task 042 — Traceroute technical design and core

- Design and implement the Android-compatible core probing approach, domain
  model, cancellation, IPv4/IPv6 selection, and deterministic tests.
- Confirm that timeout and no-response states cannot be misrepresented as a
  definitive path failure.

### Task 043 — Traceroute UI and execution

- Add the standalone Traceroute UI, real stage/progress state, start/stop
  interaction, and per-hop presentation.

### Task 044 — Traceroute interpretation and diagnostic summary

- Add cautious, evidence-based explanations for completed paths, intermediate
  non-responses, and unconfirmed later paths.
- Keep Traceroute independent from the automatic Diagnostic pipeline.

### Task 045 — v0.3.0 integration and regression

- Verify LAN enrichment does not regress v0.2.0 discovery accuracy, range
  safety, performance, History, cancellation, or network-change behavior.
- Run integration, privacy, UI, and regression checks across existing tools.

### Task 046 — v0.3.0 release candidate

- **Status: Completed.**
- **Release Candidate Regression: Passed.**

- Completed the release-readiness audit, documentation, local verification, and
  Sony Xperia 1 VII / Android 16 RC validation before release finalization.

## Quality and Release Gate

Every implementation phase must include proportionate unit tests, Gradle test,
Lint, Debug build verification, and Sony Xperia 1 VII / Android 16 validation.
An internal phase does not require a signed Release APK unless a later task
explicitly requests one.

The v0.3.0 release gate was satisfied by demonstrating:

- No regression to the frozen LAN Scanner discovery Core.
- Correct source and uncertainty semantics for all identification results.
- No cloud upload, account, or unapproved permission expansion.
- Accurate Traceroute timeout and intermediate-hop interpretation.
- Passing automated checks and recorded real-device regression results.
