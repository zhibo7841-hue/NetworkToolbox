# NetworkToolbox v0.2 Development Plan

> Status: Released
>
> Version: v0.2.0
>
> This document preserves the original v0.2 planning and delivery history.

## 1. Release Goal

V0.2 will evolve NetworkToolbox from a basic network toolkit into a network diagnostic tool.

Core principles:

- Make the default experience understandable for general users.
- Allow professional users to inspect detailed network data.
- Keep the product local first.
- Do not upload network data.

## 2. Development Priority

### Milestone 1: Basic stability

#### Issue: History Persistence

Goal: ensure that detection results are correctly persisted in local history.

The issue covers:

- Ping.
- DNS.
- TCP.
- Diagnostic Report.

The data flow must remain unified:

```text
Network Test Result
        ↓
History Repository
        ↓
History UI
```

Individual tools must not implement separate history storage paths.

### Milestone 2: Ping v2

Priority: P0

Goal: strengthen Ping as a network diagnostic capability.

#### Basic mode

- Reachability status.
- Average latency.
- Network quality.

#### Advanced mode

- Number of packets sent.
- Number of packets received.
- Packet loss rate.
- Minimum latency.
- Average latency.
- Maximum latency.
- Jitter.

Supported directions:

- IPv4.
- IPv6.
- Continuous checks.
- Stopping an in-progress check.

### Milestone 3: DNS v2

Priority: P1

Planned capabilities:

- A records.
- AAAA records.
- CNAME records.
- MX records.
- TXT records.

Displayed information:

- TTL.
- DNS server.
- Query duration.

### Milestone 4: Diagnostic Report v2

Priority: P0

Goal: evolve the report from displaying detection results into a fault-analysis aid.

The output will include:

- Current status.
- Possible causes.
- Troubleshooting suggestions.

The report must remain evidence-based and must not present possible causes as definitive diagnoses.

### Milestone 5: LAN Scanner Research

Priority: P1

This milestone is limited to technical research. It does not directly implement a LAN Scanner.

Research topics:

- Android permissions.
- Network scanning approaches.
- TCP scanning.
- mDNS.
- Device identification.
- MAC address limitations.

The current LAN Scanner v1 implementation baseline also supports an optional custom IPv4 range. Users may enter an inclusive RFC1918 start/end range of up to 254 addresses; automatic current-network scanning and custom scanning share the same bounded discovery pipeline and evidence rules. This does not expand the milestone into mDNS, MAC/OUI identification, IPv6 discovery, or unrestricted scanning.

## 3. Not Planned for Development in This Phase

### SSH/Telnet

The scope remains limited to:

- Service discovery.
- Port detection.
- Basic identification.

The following will not be developed:

- SSH terminal.
- SFTP.
- Telnet client.

## 4. Testing Strategy

Each V0.2 capability must include:

- Unit tests.
- Android tests.
- Real-device tests.

The primary real-device test target is:

- Sony Xperia 1 VII running Android 16.

Testing must continue to avoid public-network dependencies where deterministic fakes or local test targets are appropriate.
